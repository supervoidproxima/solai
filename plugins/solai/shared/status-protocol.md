# Status protocol

Shared by every card skill in this vault. Read once per run.

## 1. Status is read before the card is used for anything

Before a card enters a view, a deliverable, a table, a recount or a chain of links, read
its `status` and apply the perimeter rule for its class. Never judge a card's working
state by the file existing, by the body being full, or by something else linking to it.

The failure this exists to prevent is specific and has happened: a card left the perimeter
in frontmatter, and the prose and every aggregate carried on citing it.

## 2. A change of state is a change of status, in the same run

A skill that changes what a card says reconsiders its status in the same run. New evidence,
absorption by another card, removal from scope: these are status transitions, not edits.

## 3. State lives in the status field, never in a new field

If the existing values cannot express the state, the answer is to amend the enum in the
class declaration plus a change record. It is never to add a field. A second field holding
state is a second copy of a fact with nothing comparing the two.

## 4. A terminal card says why, in its first line

A card in a terminal status opens its body with a callout naming the reason and the date.
Frontmatter alone is not enough: a reader who scrolls past it reads prose that asserts what
the frontmatter denies.

## 5. Exclusion from a view is done by status, never by a hand-written exception

A rule like "leave GAP-007 out of the report" written into a generator or a document is
lost at the next regeneration. Set the status, and let the perimeter rule do the work.
